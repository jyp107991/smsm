# S2: the daily loop → first real use

Brief per `docs/ENGINEERING.md` §5.1. Status: S0 and S1 merged (17 Nov). Tests-first and the data layer start now; going live waits on the owner's sign-in email choice (local tests use the local mail catcher).

## Goal
The owner and partner install smsm and use it every day: sign in with a 6-digit emailed code, set up the household, add and settle shared spending, offline or online, on two phones that stay in step. Real data is safe from day one (backup download, nightly off-site backup, keep-alive).

## Criteria in scope
BAL-1…BAL-6, ADD-1…ADD-7 (ADD-8, ADD-9 are S6), SPL-1…SPL-5, MB-1…MB-3, SET-1, SET-2, SET-3, SET-5, CAT-2 (steps 1–3), CAT-3, CAT-4, ACT-1 (search and basic filters: who paid, category, dates, type), ACT-2, ACT-3, ACT-5, PPL-1…PPL-5, OFF-1…OFF-7, TXT-1…TXT-4, TXT-6, DAT-1…DAT-4, EXP-1 (the full JSON backup download only), EXP-2.

## Out of scope
Recurring, Bills, Inbox, categories editor (S3); chapters, country, places (S4: entries default to GB and everyday); Insights, recap, comments, settle day (S5); smart features (S6); CSV/PDF export and import (S7); notifications (S8).

## Screens
Sign-in (email → six-box code, paste accepted) · Start or join (join code) · Name and animal (the taken animal shows "Sam is the cat") · Home (plank, sentence, whose turn, quick add with live reading, today's entries, banners: waiting for partner, approval, changes waiting to sync, offline) · Add/edit sheet · Entry page (history, duplicate, refund this, delete) · Activity (search, filter chips, grouped by day, swipe actions) · Settle up sheet (Monzo handoff, "Did it go through?") · Settings (names and animals with "Request a change", default split request, monzo.me name, join code until full, backup download, theme, version, sign out).

## Data
- Migration: `join_household` attempt limit (a signed-in account gets 10 wrong codes per hour, so the 6-character code can't be guessed while sign-ups are open); `delete_household_if_alone` is not added (no deletes).
- After both people join: `auth-config.yml` push with `enable_signup = false` (owner told first).
- TanStack Query cache persisted to IndexedDB; mutations queued and persisted; ids made on the phone (`crypto.randomUUID`), writes are upserts; Realtime subscription per household; refetch on open, reconnect and foreground; `app_config.min_client_version` check before the first write; `navigator.storage.persist()`.
- Nightly backup: a scheduled GitHub Action exports the household's rows (service-role key held as a GitHub secret, never printed) to an encrypted file in a **private** destination (the repo is public): a private `smsm-backups` repository, or Cloudflare R2. Decide in the build and record in DECISIONS; the owner may need to add one secret.

## New packages
`@tanstack/react-query`, `@tanstack/react-query-persist-client`, `@tanstack/query-async-storage-persister` (cache, offline queue, persistence; ENGINEERING §1), `idb-keyval` (IndexedDB storage for the persisted cache and queue). Exact versions, read their installed docs before use.

## Risks
- Offline conflicts: last write wins per row, both versions in `activity` (DATA_MODEL §6). No merge logic.
- Composition keyboards: Enter during Hangul composition must not save (TXT-2); tested with composition events.
- Email delivery: depends on the owner's choice of sender; tested end to end with both addresses before calling S2 done.
- Sessions must survive long offline periods (OFF-6): no session timebox in Auth config; refresh retried on reconnect.

## Tests
Unit and component tests per criterion; the two-user end-to-end suite (Playwright, two contexts, Supabase local stack in CI, fixed clock): setup and join; identity lock and approval; add, edit, delete, undo; settle; offline entries on one phone converging on both; a full offline session including a browser restart; Hangul composition; realtime. After every scenario: the balance on screen = `core/balance` = `member_net`.
