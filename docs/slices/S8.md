# S8: notifications

Brief per `docs/ENGINEERING.md` §5.1. Released by default (owner, 17 Nov).

## Criteria in scope
NOT-1 (web push; each type its own switch; money notifications end with the balance in words; nothing about one's own changes), NOT-2 (tapping opens the thing), NOT-3's icon badge (Inbox and approvals; the shortcuts and share target shipped in S6b), ACT-4's "the partner is notified", INB-2's app-icon badge.

## Decisions made here
- **No owner steps, no new secrets.** The owner asked for nothing new to set up (17 Nov). So:
  - The VAPID key pair is made by the push function itself the first time it runs (Web Crypto, P-256) and kept in a private table `push_config` that no client role can read. The public key is read by the phones through an RPC `push_public_key()`.
  - The function is called by the database (pg_cron + pg_net). It proves the call is the database's with a random token, which the database makes for itself and keeps in `push_config`; the function reads the token with its own secret key (Supabase gives every Edge Function `SUPABASE_URL` and its secret key). No key travels through `net.http_request_queue` except that token.
  - The deploy pipeline already deploys any `supabase/functions/*` (deploy.yml). After deploying, it calls the function once with `?init=1` (idempotent: makes the keys and records its own URL in `push_config` if missing); the smoke test checks `push_public_key()` answers.
  - If the server has no pg_net or pg_cron (the SQL tests' plain PostgreSQL), the schedule is skipped, as with the nightly recurring job.
- **What is sent and when (NOT-1).** An outbox table `notification_outbox` is filled by the database, never by phones:
  - **at once** (database triggers, after insert/update): the partner added, changed, deleted or restored an entry; the partner recorded, changed or deleted a settle-up; the partner commented; a change request is waiting (always on); a decision was made on one's request.
  - **daily** (pg_cron, 08:07 London time): a shared regular payment posted today; a shared bill posts tomorrow (off by default); recap ready (the 1st, for last month) or settle day; the balance has been above the person's chosen amount for 30 days (off by default).
  The recipient is always the other member. Nothing is ever queued for the person who made the change (the actor is `auth.uid()`; the nightly recurring posting has no actor and notifies both only for "posted today").
- **Delivery.** pg_cron calls the function every minute (`* * * * *`); triggers also call it at once through pg_net, so a change arrives within seconds and the minute run catches anything missed. The function takes up to 100 unsent rows, skips types the recipient has switched off, builds the text, sends to each of the recipient's subscriptions, marks the row sent, and deletes a subscription the push service says is gone (404/410). Rows older than 2 days unsent are dropped. Sent rows are removed after 7 days.
- **Words (NOT-1, DESIGN).** Built by the function from the database at send time, with the people's names; money notifications end with the balance in words, computed from `member_net` (the database's balance, which tests prove equals the core's): "Sam added Tesco £42.50 · Sam owes Jae £24.50", "Sam changed Tesco to £45.20 · …", "Sam deleted Tesco £42.50 · …", "Sam settled up £30.00 · All square", "Sam commented on Tesco: "was this the big shop?"", "Rent £1,200.00 posted today · …", "Water £28.74 posts tomorrow", "October's recap is ready", "Settle day: Sam owes Jae £24.50", "Sam has owed Jae more than £100.00 for 30 days", "Sam asked to change the default split". Amounts formatted as the app does (`£1,200.00`); text ≤ 180 characters (a long description is cut with "…"). The pure wording lives in `src/core/notify.ts` and the function imports it (one source of truth, tested in Vitest).
- **Tapping (NOT-2).** Each notification carries a path: an entry → `/entry/<id>`; a settle-up → `/activity`; a comment → `/entry/<id>#comments`; an approval → `/settings#approvals`; a bill → `/bills`; recap → `/insights/recap/<YYYY-MM>`; settle day and balance → `/`. The service worker's `notificationclick` focuses an open window and navigates it, or opens one.
- **Icon (DESIGN).** The sender's animal head (`/icons/head-cat.png`, `/icons/head-dog.png`, rendered by `scripts/render-icons.ts` from the rig) as the notification icon; the app's badge icon (monochrome) for `badge`.
- **Switches (NOT-1).** Settings → "Notifications": "Allow notifications on this phone" (asks the browser; shows "Notifications are blocked in this browser's settings" when denied; "This phone can't show notifications" when unsupported, e.g. iOS outside an installed app), then one switch per type with its default: Entries (on), Settle-ups (on), Comments (on), Bills posted today (on), Bills tomorrow (off), Recap and settle day (on), Balance reminder (off) with an amount field (default £100.00), Approvals (always on, shown without a switch). Preferences are per person (`notification_prefs`, one row per user, RLS own row), synced between that person's phones; turning a phone off removes only that phone's subscription.
- **Subscriptions.** `push_subscriptions` (user_id, endpoint unique, p256dh, auth, created_at, last_ok_at), RLS own rows only; written by an RPC `save_push_subscription(endpoint, p256dh, auth)` (upsert by endpoint, moving an endpoint to the caller if it was another account's on the same phone) and `remove_push_subscription(endpoint)`. On every app open the phone checks its subscription still uses the current public key and re-subscribes if not.
- **Icon badge (NOT-3, INB-2).** `navigator.setAppBadge(n)` where n = open Inbox items + this phone's waiting import rows + approvals waiting for this person; `clearAppBadge()` at 0; ignored where unsupported. A push also sets the badge from a count the function sends.
- **Offline (OFF-4).** Settings says "Notifications wait for a connection" when offline; the switches still change and sync later through the queue.

## Data
- Migration `…_notifications.sql`: `pg_net` (where available); `push_config` (one row: vapid_public, vapid_private (JWK text), token, function_url; no grants to anon/authenticated); `push_public_key()` (authenticated); `push_subscriptions`, `notification_prefs` (defaults as above; `balance_threshold_pence bigint default 10000`), `notification_outbox` (id, household_id, recipient, kind, ref_id, payload jsonb, created_at, sent_at; no client grants); triggers on expenses, settlements, comments, change_requests; `queue_daily_notifications()` (security definer, cron only); `kick_push()` (pg_net POST to the function with the token; no-op when not set up); cron jobs `smsm-push` (every minute) and `smsm-notify-daily` (`7 7,8 * * *` UTC with a London-hour check so it runs once at 08:07 London time year-round); RPCs `save_push_subscription`, `remove_push_subscription`, `set_notification_prefs(jsonb)`.
- Edge Function `supabase/functions/push/index.ts` (Deno): `?init=1` setup; POST with the token drains the outbox; imports `src/core/notify.ts` for wording (if the functions bundler can't reach `src/`, a script copies it into `supabase/functions/_shared/` and a test fails when the two differ); web push with a maintained Web-Crypto library (read its current docs; record the version in DECISIONS).
- Core `src/core/notify.ts`: `notificationText(kind, data, names) → { title, body, path }`, `balanceWords`.
- Data: `notificationPrefs()`, `setNotificationPref(kind, on | amount)`, `enablePush()`, `disablePush()`, `pushState()` (`'unsupported' | 'blocked' | 'off' | 'on'`), `badgeCount()`.
- Service worker (`public/share-target.js` pattern, a new `public/push.js` via `importScripts`): `push` shows the notification (title, body, icon, badge, data.path, tag per ref so a later change replaces an earlier one), `notificationclick` opens the path.

## Tests
- Core: every kind's wording (names, amounts, balance words, "All square", cut at 180 with "…", sentence case), paths.
- SQL: triggers queue for the partner only, never the actor; each kind; switches respected at send selection (`next_notifications(limit)` the function calls returns only enabled kinds); daily job (posted today both members, tomorrow, recap on the 1st, settle day, 30-day balance rule); RLS (subscriptions and prefs own rows; outbox and config unreadable by clients); `push_public_key()`; RPCs.
- Function: unit-tested in Vitest with a fake fetch and fake database (init idempotent; wrong token refused; drains, marks sent, drops 404/410 subscriptions, skips switched-off kinds).
- Data/screens: Settings Notifications (unsupported, blocked, off → allow, switches, amount), prefs sync through the queue, badge count.
- E2E: Settings → Notifications at 320/390 in both themes with axe; the service worker's push and click handlers (dispatch a synthetic push event in the browser test and check the notification and navigation).

- Core: `notificationText`, `balanceWords` in `src/core/notify.ts`.
- Data: as above. SQL: as above.
